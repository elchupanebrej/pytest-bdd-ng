## Phase 6 - Wave 0: Run Access, Error Reporting & Failure Paths

**Objective:** Integration tests for scenario failure paths, run access patterns,
error reporting integration, and the critical `require_*` fallback chains that
connect `ScenarioRun` to `FeatureRuntimeBinding` to `Run`.

**Why this matters:** Error paths are where bugs hide longest. The `require_active_scenario_run`,
`require_feature_binding`, `require_gherkin_document`, and `require_pickle_object` chains
are exercised in production every time something goes wrong, but have no integration tests.
When these fail, users get cryptic `RuntimeError` messages. We need to verify:
1. The error messages are clear and actionable
2. The `ContextErrorState` codes are correct for each failure mode
3. Reporting context snapshots degrade gracefully when data is missing

**Output:** Test file:
- `tests/feature/test_run_access_and_errors.py` — error path and reporting integration tests

## Trust Boundaries

- Error message stability — RuntimeError messages from require_* methods are part of
  the public contract. Tests must assert on message content, not just exception type.
- Exception propagation — Step errors must propagate through the full hook pipeline
  without swallowing original traceback.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation |
|-----------|----------|-----------|-------------|------------|
| T-06-07 | Tampering | Step error hides original exception | mitigate | Assert exception chain preserved via `__cause__` |
| T-06-08 | Information Disclosure | Error messages leak internal paths | mitigate | Verify messages are user-facing, not stack traces |
| T-06-09 | Denial of Service | Unhandled RuntimeError in cleanup crashes next scenario | mitigate | Test sequential scenario execution |
</threat_model>
