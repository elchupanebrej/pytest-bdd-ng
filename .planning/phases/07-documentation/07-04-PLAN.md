Cover these 10 breaking changes (D-11):
1. **Step definition decorators**: @given, @when, @then, @step are now lazy-loaded via __getattr__ — import from pytest_bdd works the same, but internal module structure changed
2. **target_fixture replaces implicit Given fixtures**: In pytest-bdd 3.x, @given steps automatically became fixtures. Now must use target_fixture explicitly. Before: `@given("user exists")` creates `user` fixture. After: `@given("user exists", target_fixture="user")`.
3. **Parser syntax: {var} replaces <var>**: Angle bracket template syntax replaced by curly brace syntax with parsers.parse(). Before: `@given("user <name> exists")`. After: `@given(parsers.parse("user {name} exists"))`.
4. **example_converters moved to step-level converters**: example_converters on @scenario deprecated. Use converters parameter on step decorators instead. Before: `@scenario(..., example_converters={"count": int})`. After: `@given(parsers.parse("I have {count} items"), converters={"count": int})`.
5. **Hook signature changes**: Original pytest-bdd hooks use (feature, scenario) objects. pytest-bdd-ng hooks use (request, Run) objects with cucumber_messages types. Show before/after for a typical hook.
6. **Plugin architecture**: Original uses function-based plugin registration. pytest-bdd-ng uses class-based pattern (class + entrypoint.py + hook.py). Show minimal plugin example.
7. **StashBound pattern for config**: pytest-bdd-ng uses StashBound base class for pytest.config.stash access. Show how to subclass StashBound vs original ad-hoc config storage.
8. **Cucumber Messages integration**: pytest-bdd-ng emits Cucumber Messages protocol (NDJSON) for formatter integration. Original did not. Show how to consume messages.
9. **CLI flag changes**: --cucumberjson removed (replaced by --cucumber-json-formatter via class-based plugin entrypoint). Show new flag usage.
10. **Allure plugin removed**: Dead Allure logger plugin removed. Users needing Allure should use external pytest-allure plugin.

Keep the guide concise — quick-reference style. Each change should be 5-10 lines maximum including code examples. Target 50-100 lines total.

Do NOT include: exhaustive API diffs, every minor change, internal architecture details (those belong in DEVELOPMENT.rst).
