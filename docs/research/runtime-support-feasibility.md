# Runtime support feasibility

**Date:** 2026-10-13

**Context:** [runtime support issue #315](https://github.com/elchupanebrej/pytest-bdd-ng/issues/315) · [runtime policy map #313](https://github.com/elchupanebrej/pytest-bdd-ng/issues/313)

## Finding

The three lanes are feasible to investigate in required CI, but only CPython 3.15 has a strong package-install path today. PyPy 3.12 and GraalPy 25.3 can be provisioned on Linux x86_64, but the mandatory Pydantic native dependency has no wheel for either exact target. Both alternate lanes therefore depend on an unverified source build of `pydantic-core`, and neither can yet be claimed installable or behavior-compatible. GraalPy also conflicts with the product workflow's unconditional pip upgrade. No install or test was run for this research note.

## Repository facts

- [`pyproject.toml`](../../pyproject.toml) declares `requires-python = ">=3.10"`, classifiers through CPython 3.14, and mandatory `aiohttp`, `gherkin-official>=25,<30`, `pytest>=5.2`, and Pydantic. The PyPy marker caps Pydantic below 2.13; its comment explains the cap as a workaround for missing PyPy 3.10 wheels. Pydantic is used by product code, so `pydantic-core` is a required native dependency, not an optional integration.
- [`tox.ini`](../../tox.ini) currently defines CPython through 3.13 and PyPy 3.10. Its test environments install `[struct-bdd]`, `[test]`, and `[doc-gen]` by default, with Allure variants; the GitHub Actions Python map has no 3.15, PyPy 3.12, or GraalPy entry.
- [`.github/workflows/main.yml`](../../.github/workflows/main.yml) currently runs CPython 3.10–3.13 and PyPy 3.10 across Ubuntu, Windows, and macOS with older CPython OS exclusions. It uses `actions/setup-python@v5` and runs `python -m pip install --upgrade pip` before tox. CI currently installs and exercises the optional extras above, so it does not yet express a core-only alternate-runtime contract.
- There is no committed lockfile in this checkout. Exact transitive versions, including the selected Pydantic and `pydantic-core`, depend on the resolver at install time.

## Compatibility details and confidence

**Verified upstream facts:** pytest lists official Python 3.15 support. PyPy 8.0.0 released Python 3.12 support as beta and provides Linux x86_64 downloads. GraalPy 25.3 is Python 3.13.14 and recommends Linux; its release notes identify expanded `pydantic-core`/PyO3 support. `actions/setup-python` supports PyPy/GraalPy selectors. ([pytest changelog](https://docs.pytest.org/en/stable/changelog.html), [PyPy announcement](https://pypy.org/blog/), [GraalPy docs](https://www.graalvm.org/latest/python/docs/), [setup-python advanced usage](https://github.com/actions/setup-python/blob/main/docs/advanced-usage.md), [GraalPy changelog](https://github.com/oracle/graalpython/blob/master/CHANGELOG.md))

**Verified artifact facts:** inspected PyPI release-file listings show `pydantic-core` 2.41.5 has PyPy 3.10/3.11 and GraalPy 3.11/3.12 wheels; the current 2.50.1 listing includes CPython 3.15, PyPy 3.11, and GraalPy 3.12, but not PyPy 3.12 or GraalPy 3.13. Both versions publish sdists. The 2.41.5 build metadata uses Maturin and PyO3 0.26. ([2.41.5 files](https://pypi.org/project/pydantic-core/2.41.5/), [current release files](https://pypi.org/project/pydantic-core/), [Maturin build config](https://github.com/pydantic/pydantic-core/blob/v2.41.5/pyproject.toml), [PyO3 version in Cargo metadata](https://github.com/pydantic/pydantic-core/blob/v2.41.5/Cargo.toml))

**Inference, not verified compatibility:** Because the required Pydantic dependency can fall back to a source distribution, a missing wheel does not itself prove installation is impossible. The release notes and build metadata make native builds plausible, but only clean installs on the exact target runtimes can establish whether the current dependency graph builds. Similarly, a pure-Python Gherkin package and the `aiohttp` fallback do not establish that pytest plugins, fixtures, or the product's tests behave correctly on those runtimes.

## Acceptance evidence for the implementation ticket

1. Capture the interpreter implementation/version and the exact resolved dependency set for each new lane. Keep CPython 3.15 on the existing supported OSes; keep PyPy 3.12 and GraalPy 25.3 on Linux x86_64.
2. From clean CI environments, install the product plus required test dependencies only. Save artifact/build logs for `pydantic-core` and any other native package. For GraalPy, do not run the workflow's pip upgrade step.
3. Run the agreed core suite and at least one executable product example on every lane. An install-only green job is insufficient evidence for the stated support contract.
4. Report `struct-bdd`, `doc-gen`, and Allure as supported or unsupported per alternate runtime based on separate jobs; don't infer their support from core success.
5. Confirm the exact pinned `actions/setup-python` version can provision CPython 3.15 on every retained OS and PyPy/GraalPy on Linux. If the existing action cannot resolve a new interpreter, update the action or use a documented explicit runtime download.
