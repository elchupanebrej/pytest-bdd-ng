# Non-Implementable Governance Criteria (CI Policy)

**Scope**: `specs/008-maximize-messages-coverage/contracts/capability-decisions.json` decisions consumed by `pytest_bdd.script.message_capability_governance report`.
**Goal**: prevent unsupported capabilities from being deferred without objective, reproducible proof.

## 1. Eligibility Rules

A capability may be marked `Non-Implementable` only if all rules pass:

1. `capability_id` exists in canonical inventory `I`.
2. Capability is not in runtime-required set `R`.
3. Capability is not observed in runtime evidence set `O` generated by dedicated audit suite.
4. Decision has complete metadata: `rationale`, `decision_owner`, `evidence_refs`, `reviewed_at`, `recheck_trigger`.
5. Decision has hard-issue proof bundle (Section 2).

Formal condition:

- `NI ⊆ (I - R - O)`

Where `NI` is capability IDs with status `Non-Implementable`.

## 2. Hard-Issue Proof Bundle (Objective Evidence)

Each `Non-Implementable` decision MUST include objective hard-issue evidence:

1. `rationale` includes a concrete limitation statement with:
   - runtime surface (`pytest hook`, `cucumber-messages envelope`, or parser boundary),
   - why extraction is impossible now,
   - what concrete change would make it possible.
2. `evidence_refs` contains at least 3 references with distinct evidence classes:
   - Runtime absence proof: NDJSON artifact or query result showing capability is not observed.
   - Surface constraint proof: source/hook/spec reference showing required signal is unavailable.
   - Governance trace proof: tracker item/spec note linking ownership and follow-up.
3. `decision_owner` is a stable team or maintainer group identifier.
4. `reviewed_at` is RFC3339 timestamp and inside active release cycle.
5. `recheck_trigger` is from controlled set:
   - `runtime-hook-surface-change`
   - `messages-schema-change`
   - `pytest-upgrade`
   - `python-version-matrix-change`
   - `scheduled-revalidation`

## 3. Recheck Policy

`Non-Implementable` is temporary and must be revalidated.

1. Every decision is rechecked when its `recheck_trigger` condition occurs.
2. Every decision is rechecked on schedule even without trigger:
   - max age: 30 days from `reviewed_at`.
3. Decision becomes invalid (effective `Pending`) when:
   - `reviewed_at` is older than 30 days, or
   - baseline diff includes this `capability_id` in added/changed set, or
   - matching trigger condition is detected in current CI run.

## 4. CI Gate Contract

CI MUST fail when any condition is true:

1. `Non-Implementable` capability is in `runtime-required-capability-ids.txt`.
2. `Non-Implementable` capability is observed in current runtime NDJSON evidence.
3. Proof bundle is incomplete (missing evidence class, owner, or stale review date).
4. `recheck_trigger` is missing or not in allowed trigger set.
5. Trigger event occurred but decision was not re-reviewed after trigger date.

## 5. Gate Execution Order

1. Generate runtime evidence NDJSON from dedicated suite.
2. Generate governance report with strict flags:
   - `--require-runtime-required-covered`
   - `--require-non-runtime-classified`
   - `--require-fully-governed`
3. Run Non-Implementable hard-issue gate:
   - validate `NI ⊆ I - R - O`,
   - validate evidence classes and timestamp freshness,
   - validate recheck trigger policy.
4. Run weekly baseline diff gate and force NI recheck for changed capabilities.

## 6. Repository Fit Notes (Current State)

As of 2026-03-03, the current decisions file contains only `Non-Implementable` statuses and uses one repeated rationale/trigger pattern. This policy requires capability-specific proof bundles and periodic freshness rechecks to keep those decisions auditable and non-stale.
